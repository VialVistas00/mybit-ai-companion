# 流式分段上传可行性分析

**问题**：能否边录音边分段上传，比如每 1 秒传一次？

**结论**：**当前硬件和固件条件下不可行**，但有一条替代路径。

---

## 一、为什么不可行

### 1.1 固件不支持流式录音

这块板子的 `audio` 模块只有同步阻塞接口：

```python
audio.recorder_init()
audio.record('x.wav', 2)      # 阻塞 2 秒，一次性录完整个文件
audio.recorder_deinit()
```

**没有** `record_start()` / `record_chunk()` / `read_buffer()` 这类流式 API。

这意味着：**你无法在录音进行中拿到中间数据**。必须等 `record()` 返回，才能读文件。

### 1.2 `_thread` 实际不可用

之前的测试记录（`docs/问题与解决记录.md`）：

```
_thread.start_new_thread 不调度（box[0] 恒为 0）
```

即使有流式 API，也无法用一个线程录音、另一个线程上传。

### 1.3 内存限制

```
2 秒录音 → 32812 字节，需要 32KB 连续块
3 秒录音 → 49196 字节，需要 49KB 连续块 → MemoryError
```

如果做 1 秒分段缓冲，需要保留「正在录」+「正在传」两份数据，**内存直接翻倍**，2 秒就会 OOM。

### 1.4 上传时间本来就不是瓶颈

实测数据：

| 环节 | 耗时 |
|---|---|
| 断句检测 + 连接 | ~115 ms |
| 上传 32812 字节 | 1.6 ~ 3.1 秒 |
| whisper 识别 | 0.2 ~ 0.4 秒 |
| DeepSeek 回答 | 1.7 ~ 2.0 秒 |
| **合计** | **约 5 秒** |

**录音 2 秒 + 上传 2 秒 = 4 秒**，流式最多省掉「录音结束后的等待」，收益约 1~2 秒。

而实现代价是：
- 需要改固件（厂商定制，无源码）
- 或者引入内存翻倍风险
- 复杂度大幅上升（分片重组、乱序处理、失败重传）

**投入产出不划算。**

---

## 二、可行的替代方案

### 方案 A：缩短录音时长，提高识别率（推荐）

当前 2 秒是内存上限。但可以用**自动断句**代替固定时长：

```
按 A 键 → 开始录音 → 检测到静音超过 0.5 秒就停止 → 上传
```

问题：`audio.record()` 不支持提前停止。

**变通**：录 2 秒，然后在服务器端用 VAD 裁掉首尾静音，只识别有声部分。这样虽然录 2 秒，但识别的是真实说话内容。

**代价**：无。已经实现了（服务器端 `vad_filter=True`）。

### 方案 B：预连接，省掉建连时间

当前每次上传都要重新 `connect()`（实测 9~11ms，不算慢）。

但可以在**录音的同时**建立 TCP 连接（`record()` 是阻塞的，不能并行）。

**不可行**，同上原因。

### 方案 C：换板子

ESP32-S3 + PSRAM（8MB）的板子：

- 支持 I2S 流式录音
- 内存充足，可缓存 30 秒音频
- MicroPython 官方支持 `I2S.readinto()`

这样就能做真正的流式上传。但要换硬件。

### 方案 D：让板子只做「录音触发」

极简方案：板子只负责检测「有没有声音」和「按了键」，录音交给电脑。

但这违背了「无线独立」的初衷。

---

## 三、如果真的要做流式

假设固件支持（比如换 ESP32-S3），实现思路：

### 板子端

```python
# 伪代码
audio.record_start('pcm', 8000)      # 不阻塞

seq = 0
while recording:
    chunk = audio.read_chunk(16000)   # 读 1 秒 = 16000 字节
    if not chunk:
        break
    relay.send_chunk(seq, chunk)      # 分片上传
    seq += 1
audio.record_stop()

relay.finish(seq)                     # 通知结束，等识别结果
```

### 服务器端

需要新增分片接口：

```python
@app.route("/api/upload/chunk", methods=["POST"])
def api_upload_chunk():
    sid = request.args.get("sid")      # 会话 id
    seq = int(request.args.get("seq"))
    data = request.get_data()

    buf = SESSIONS.setdefault(sid, {})
    buf[seq] = data

    # 尝试合并
    merged = b""
    i = 0
    while i in buf:
        merged += buf[i]
        i += 1
    if i > 0:
        del buf[0:i]

    return jsonify({"ok": True, "received": seq, "total": len(merged)})
```

### 延迟收益

| 方案 | 首次响应时间 |
|---|---|
| 当前（录完再传） | 2.0（录音）+ 2.0（上传）+ 0.3（识别）+ 2.0（AI） = **6.3 秒** |
| 流式 | 2.0（录音与上传重叠）+ 0.3 + 2.0 = **4.3 秒** |

**节省约 2 秒。**

但同时引入：
- 分片丢失/乱序处理
- 内存压力（需缓存正在录的数据）
- 代码复杂度翻倍

---

## 四、结论

| 问题 | 答案 |
|---|---|
| 现在能做流式吗 | ❌ 固件不支持，`_thread` 不可用，内存不够 |
| 值得做吗 | ❌ 只省 2 秒，代价是复杂度翻倍 |
| 有没有更划算的 | ✅ 缩短录音时长（已经 2 秒）、服务器端 VAD 裁静音（已实现） |

**建议**：保持现状。如果将来换 ESP32-S3（带 PSRAM）的板子，再做流式。
