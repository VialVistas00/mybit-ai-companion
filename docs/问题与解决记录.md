按**发生顺序**记录这个项目从开始到现在的完整过程。每一条都对应真实发生过的问题，包含当时的错误判断、排查过程和最终结论。

## 阶段一：面对一堆散落的课程材料

### 问题 1：目录里到底是什么

起点是一个 200 多个文件的目录 `D:\数据文件\上课\信电导论`，包含两份实验课 PPT、20 个手册样例、产品手册、固件包、作业代码、AI 学习材料、农业大棚项目。

**怎么做的**：用 python-pptx / python-docx 把 PPT 和 Word 的文本大纲全提取出来，输出成 markdown，再通读。发现所有内容都指向同一块硬件——MYBIT 信息科技实验板（ESP32）。

**收获**：课程结构清楚了（实验一到实验十二、作业一电子时钟、作业二 microdot 网站），以及厂商是杭州纳茵特（RobotEdu），技术支持电话 0571-YOUR_WIFI_PASSWORD。

### 问题 2：板子到底能不能通

不确定 IDE 是不是独占串口、板子是不是活的。

**做法**：先只用只读操作探测——串口握手、`os.uname()`、`gc.mem_free()`、I2C 扫描。确认：

```
MicroPython 1.13.0 / npython with ESP32 / v1.06.5 on 2024-07-31
I2C: 0x38(AHT20) + 0x3c(SSD1306)
空闲内存 89232 B
```

**遇到的绊子**：这个固件的 REPL **不支持多行粘贴**。一开始把多行代码用 `\r\n` 拼接发送，全部 `SyntaxError`。后来改成两种方式：

- 单行命令直接发
- 多行用 `exec(open('file.py').read())`

再后来写 `mybit.py` 时才用上 raw REPL 的正确姿势。

## 阶段二：第一个可玩的东西

### 问题 3：贪吃蛇按键没反应

烧了贪吃蛇之后，按 A/B 完全没反应，屏幕停在最后一帧。

**第一反应**：以为按键坏了。写了一堆诊断代码往串口打按键值，发现串口里读到的全是 `0`。

**真正的排查**：让程序把按键电平变化写进板子上的 `/keylog.txt`。后来翻日志看到：

```
boot A=0 B=0
t=377 A=1 B=0     ← 你按下了 A，被正确读到
start
```

**按键是好的。** 那问题在哪？

继续查文件系统，发现 `main.py` 不见了：

```
板载: ['boot.py', 'microdot.py', 'temphtml.py']    ← main.py 消失了
```

**根因找到了。** 出厂 `boot.py`：

```python
_button_a = machine.Pin(21, machine.Pin.IN)
if _button_a.value() == 1:
    os.remove("/main.py")
```

本意是「应急清程序」，但贪吃蛇要按 A 转向，只要板子恰好在这瞬间重启（开关串口、USB 供电抖动都算），程序就被删了。

**解决**：换成安全版 `boot.py`，保留引脚检测但不再删文件。

**教训**：现象是“按键没反应”，根因却是“程序根本不在”。诊断时不要预设原因。

### 问题 4：音频 API 的阻塞特性

想让贪吃蛇有音效，先测了三个 API：

```
beep.time(200)   -> 阻塞 889 ms
beep.time(1000)  -> 阻塞 642 ms
beep.time(2000)  -> 阻塞 1644 ms

music.pitch(1500, 30)  -> 阻塞 98 ms
music.play(JUMP_UP)    -> 阻塞 645 ms
music.play(POWER_UP)   -> 阻塞 3011 ms
```

`beep.time()` 的阻塞时间跟参数没有线性关系（200 反而比 1000 慢），完全不可控。**游戏里绝对不能用**。

最终用 `music.pitch(freq, ms)` 做短音效，`music.play()` 只用在开局/结束。

## 阶段三：转向 AI 学伴，撞上联网这堵墙

### 问题 5：板子连不上任何东西

这是整个项目花时间最多的部分，试了四条路。

#### 路线一：板子直连校园网 Wi-Fi

能连上，也能拿 IP：

```
ifconfig = ('BOARD_IP', '255.255.0.0', 'CAMPUS_GW', 'CAMPUS_DNS')
```

但有个 Portal 网页认证，未认证时**只放行 80/443，其他端口全挡**：

```
板子 -> SERVER_IP:9446  → EHOSTUNREACH
板子 -> SERVER_IP:8080  → EHOSTUNREACH
板子 -> SERVER_IP:80    → 通，但返回的是 Portal 劫持页
```

劫持页内容：

```html
<script>location.href="http://PORTAL_IP/index_1.html"</script>
Authentication is required.
```

**结论**：不完成认证，什么也做不了。

#### 路线二：板子连电脑（同网段）

```
板子 BOARD_IP → 电脑 PC_IP:8080 → EHOSTUNREACH
```

**校园网做了 AP 隔离**，同网段设备不能互访。

#### 路线三：电脑开热点

Windows 移动热点能开起来（`HOTSPOT_IP`），但：

```
netsh wlan show drivers → Hosted network supported: No
```

这块 Intel AX203 **不能同时做 STA 和 AP**。电脑一旦连板子的 AP，就断了外网——**我因此掉线过一次**，用户在会话里提醒「刚才因为电脑完全连接到板子，无线网断了，你掉线了」。

#### 路线四：死磕 Portal 认证（最曲折）

反向分析 Portal 前端，把 SRun 协议完整拆了出来：

```
1. GET /cgi-bin/get_challenge?username=X&ip=Y  → token（60秒有效）
2. hmd5   = HMAC-MD5(key=token, msg=password)
3. info   = {SRBX1} + base64(xxtea(json, token))
4. chksum = SHA1(token+user+token+hmd5+token+acid+token+ip+token+n+token+type+token+info)
5. GET /cgi-bin/srun_portal?action=login&...
```

**怎么确定 hmd5 是 HMAC-MD5**：直接用 Playwright 打开认证页，在浏览器里调页面自己的 `md5()` 函数，取三组样本对比：

```
md5('aaa','bbb')        = REDACTED_32HEX
hmac_md5('bbb','aaa')   = REDACTED_32HEX   ← 完全匹配
md5('aaa'+'bbb')        = REDACTED_32HEX   ← 不匹配
md5('bbb'+'aaa')        = REDACTED_32HEX   ← 不匹配
```

三组样本 + 一个真实 token 全部匹配，确定无疑。

**xxtea 也验证到 0 差异**：hook 页面的 `$.base64.encode`，抓到它加密的输入密文，用同一个 token 同明文对比：

```
浏览器密文长度: 104
我的密文长度:   104
差异字节数:     0 / 104
```

**但认证还是失败**，返回 `auth_info_error`。

**关键对照实验**——证明跟密码无关：

```
YOUR_STUDENT_ID + 正确密码   → auth_info_error
YOUR_STUDENT_ID + 错误密码   → auth_info_error   ← 一模一样
YOUR_STUDENT_ID + 空密码     → auth_info_error
不存在的账号         → auth_info_error
```

而且后来**浏览器自己也失败了**：

```
浏览器(Chromium) → login_error / "INFO failed, BAS respond timeout."
手机(真实)       → 成功
```

**最终结论**：算法层面 100% 正确（逐字节验证），但服务端对「脚本 / 模拟浏览器」有额外限制，`BAS respond timeout` 说明请求到达了 RADIUS 层但接入服务器无响应。这属于服务端策略，不是协议问题。

`pc/srun_client.py` 保留了完整实现，环境变了可以直接用。

#### 最终方案：USB 串口

放弃无线：

```
板子 ──USB串口(COM3)── 电脑 ──校园网── 外网
```

绕开 AP 隔离、绕开 Portal，也不影响电脑上网。**实测 1 秒完成往返。**

## 阶段四：麦克风的反复打脸

### 问题 6：以为麦克风坏了（错误判断）

第一次烧 AI 学伴，屏幕显示「无麦克风模块」。开始排查：

| 排查项 | 结果 |
|---|---|
| `import microphone` | ❌ 模块不存在 |
| `sound.read()` 连续 40 次 | ❌ 恒为 0 |
| 录音 WAV 分段峰值 | ❌ 恒定 325（播放语音时也只到 549） |
| 各 ADC 通道对比 | GPIO34/35/36/39 都有波动，**只有 GPIO37 恒为 0** |

`sound` 的实际类型是 `ADC(Pin(37))`。据此**判定麦克风硬件故障**，还建议用户报修换板。

**用户直接纠正了我**：「麦克风是好的，你犯了很严重的错误」。

### 问题 7：找到真正的录音接口

重新挖固件，发现 `audio` 模块：

```python
import audio
audio.recorder_init()
audio.record('x.wav', 3)      # 参数是 (文件名, 秒数)
audio.recorder_deinit()
```

实测生成 **49196 字节** WAV：8kHz / 16bit / 单声道 / 3.07 秒。

**我的第一轮判断错在哪**：`sound` 是 `ADC(Pin(37))`，而这块板的麦克风走 **I2S**，根本不经过 ADC 通道。所以 `sound.read()` 读 0 是**正常现象**，不能据此判断硬件损坏。

### 问题 8：录音录到 4 秒就崩

```
3 秒 -> OK 49196 bytes
4 秒 -> MemoryError
5 秒 -> MemoryError（还会警告 "Record time too long, will limit to 5s"）
```

怪异的是当时 `gc.mem_free()` 显示还有 **75 KB**。

**原因**：不是总量不够，是**堆碎片**——拿不到连续的 4KB 块。

**解决**：录音前连做两次 `gc.collect()`，并把录音时长固定为 3 秒。

### 问题 9：识别结果永远是空

把 WAV 送去 whisper，识别结果是空字符串。分析波形：

```
直流偏置:      -8567      ← 整体被拉到 -8567 附近
真实信号幅度:  只有 ±330
开头 62、63 号样本: 36551   ← 启动瞬间的巨大尖峰
```

按绝对峰值归一化，会把真实语音压到几乎听不见。

**解决**：三步处理

```python
mean = sum(s) // n
centered = [v - mean for v in s]        # 1. 去均值
for i in range(min(120, n)):
    centered[i] = 0                      # 2. 裁掉启动尖峰
mags = sorted(abs(v) for v in centered)
peak = mags[int(len(mags) * 0.95)]       # 3. 用 95 分位数做稳健峰值
scale = 0.6 * 32767.0 / peak
```

处理后峰值从 330 提升到 19660，语义保留完好。

## 阶段六：工程实现中的坑

### 问题 12：一次性 base64 整段 WAV 直接 OOM

最初 `send_wav` 把整个 WAV 的所有分片转成 base64 存进 list：

```python
parts = []
while True:
    b = f.read(CHUNK)
    if not b: break
    parts.append(base64encode(b))     # 全存下来
```

49KB 的 WAV 变成 65KB 字符串，超过 60KB 可用堆 → `MemoryError`。

**解决**：改成流式，读一片发一片丢一片：

```python
n = (size + CHUNK - 1) // CHUNK
send("MSG|S|%d" % n)
f = open(path, "rb")
i = 0
while i < n:
    b = f.read(CHUNK)
    send("MSG|D|%d|%s" % (i, b64.b2a_base64(b).strip().decode()))
    del b
    i += 1
    if i % 20 == 0:
        gc.collect()
```

**实测**：49196 字节完整发出 274 块，内存剩余 80KB，无异常。

### 问题 13：串口传输慢到 7.3 秒

测了串口写入速度：

```
250 字符/行 ≈ 27 ms/行
274 行 × 27ms = 7.3 秒
```

这是 USB 串口 REPL 的**字符回显开销**，无法通过代码消除。

**缓解**：分片调到 180 字节/片（base64 后 240 字符），这是块数和单块开销的平衡点。再小则块数变多总量不变，再大则单行超时。

### 问题 14：REPL 卡在 raw mode 出不来

调试中途板子进了 raw REPL 没退出，后续所有命令都无响应：

```
RuntimeError: raw REPL 未就绪: b''
```

**解决**：发 `\x02`（Ctrl-B）退出 raw REPL，再 `\x03`（Ctrl-C）中断。

### 问题 15：桥和测试脚本抢串口

`pyserial` 是独占打开的，桥在跑的时候测试脚本连不上：

```
SerialException: could not open port 'COM3': PermissionError(13, '拒绝访问。')
```

**解决**：所有测试脚本启动前先 `taskkill` 掉 `serial_bridge` 进程，或改用「桥自己带 --selftest 参数」的方式，让桥在一次会话里完成全流程。

### 问题 16：`\x05` 进的是 paste mode 不是 raw REPL

想让板子执行文件，发了 `\x05`（Ctrl-E），结果：

```
paste mode; Ctrl-C to cancel, Ctrl-D to finish
=== exec(open('selftest.py').read())
===
```

命令根本没执行。这个固件的 `Ctrl-E` 是 paste mode。

**解决**：普通 REPL 下直接发 `exec(open('file.py').read())\r\n` 就行，不用进 raw。

## 阶段七：固件升级翻车

### 问题 17：刷固件把板子刷成砖

目录里有 `firmware-v1.06.6.5.bin`（5.8MB），想升级试试能不能修复麦克风。

```bash
esptool --port COM3 write_flash 0x0 firmware-v1.06.6.5.bin
```

**刷完无限重启**：

```
invalid header: 0x6d305b1b
invalid header: 0x6d305b1b
rst:0x10 (RTCWDT_RTC_RESET),boot:0x12 (SPI_FAST_FLASH_BOOT)
```

**原因**：这个 5.8MB 文件不是完整的整片镜像，从 `0x0` 烧会覆盖引导区。

分区表（从 `0x8000` 读到）：

```
nvs       0x009000   24 KB
phy_init  0x00f000    4 KB
factory   0x010000  1.7 MB   ← 应用固件应该烧这
vfs       0x200000    2 MB   ← 文件系统
```

### 问题 18：好在我提前备份了

刷之前做过全片备份：

```bash
esptool --port COM3 --baud 460800 read_flash 0x0 0x800000 flash_full_backup.bin
# 8388608 字节，MD5 D65821CCB70DE000BE629A702D7FC4B0
```

写回：

```bash
esptool --port COM3 --baud 460800 write_flash 0x0 _board_backup/flash_full_backup.bin
```

**板子完全恢复**，文件系统和固件都正常。

**教训**：刷固件前必须 `read_flash` 全片备份，这是唯一能救回来的办法。

## 阶段九：教学环境里的小问题

### 问题 21：Windows 凭据与 SSH

推送到 GitHub 时遇到：

```
ssh -T git@github.com  →  Connection timed out during banner exchange
```

**22 端口被校园网封了**。改用 `ssh.github.com:443`：

```
Host github.com
  HostName ssh.github.com
  Port 443
```

又遇到第二层问题：**一把 SSH 公钥只能绑定一个 GitHub 账号**。原来的 `id_ed25519` 绑在 `YOUR_SSID` 上，仓库却在 `YOUR_SSID00` 下：

```
ERROR: Permission to YOUR_SSID00/mybit-ai-companion.git denied to YOUR_SSID.
```

**解决**：新生成 `id_ed25519_00` 专门绑 `YOUR_SSID00`，配置文件里指定 `IdentityFile`。

### 问题 22：PowerShell 写 UTF-8 文件带 BOM

`Set-Content -Encoding UTF8` 在 Windows PowerShell 5.1 下会写 BOM，导致：

```
/c/Users/.../.ssh/config: line 1: Bad configuration option: \357\273\277host
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM
```

**解决**：用 .NET 的 `UTF8Encoding($false)`：

```powershell
[IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding($false)))
```

**后续影响**：所有生成板子代码、配置文件的地方都改成了 Python 写文件（Python 默认无 BOM）。

## 总结：这个项目教了什么

| 教训 | 具体表现 |
|---|---|
| **现象不等于原因** | “按键没反应”实际是“程序被删了” |
| **不要凭单一信号下结论** | 用 `sound.read()` 判断麦克风坏了，实际麦克风走 I2S 不经 ADC |
| **资源限制要分清总量和碎片** | 75KB 空闲也拿不到 4KB 连续块 |
| **有损信号要预处理** | 音频有 -8567 直流偏置，不处理识别全空 |
| **协议分析要逐字节验证** | HMAC-MD5 靠三组样本比对才确定，猜不出来 |
| **危险操作先备份** | 刷固件翻车后靠 8MB 全片备份救回 |
| **客户端差异是真实存在的** | 同样的算法，浏览器和脚本的待遇不同 |

## 阶段十：无线独立运行（最终突破）

这一阶段的前提是拿到一个别人写的 `hzcuwifi.zip`，里面直接给出了正确方向。

### 问题 23：找了半天，攻击错了认证系统

之前花了大量时间攻 SRun（`10.69.255.190`），把 HMAC-MD5、xxtea、SHA1 全部逆出来了，逐字节验证一致，但服务端始终返回 `auth_info_error` / `BAS respond timeout`。

那个压缩包里是另一套：

```
Dr.COM：http://10.69.255.130/drcom/login?DDDDD=账号&upass=密码&0MKKey=123456
SRun  ：http://10.69.255.190/cgi-bin/srun_portal?action=login&password={MD5}...
```

**两套完全不同的系统，不同的服务器，不同的协议。**

实测 Dr.COM 直接返回真实数据：

```json
{"result":1,"v46ip":"10.67.65.105","uid":"YOUR_STUDENT_ID","stime":"2026-11-04 05:55:24"}
```

**但板子还是不行。** 板子连 `HZCU-IPV6` 后拿到 `10.60.204.201`，访问 `10.69.255.130` 被劫持到 Portal。

### 问题 24：关键在于连哪个 SSID

反复试了各种参数组合都失败后，转向测试另一个 SSID：

```
板子连 HZCU-IPV6 → 10.60.204.201 → 访问 10.69.255.130 被劫持
板子连 HZCU      → 10.67.229.247 → 访问 10.69.255.130 正常返回 JSON
```

**`HZCU` 和 `HZCU-IPV6` 是两套完全独立的认证体系：**

| | HZCU-IPV6 | HZCU |
|---|---|---|
| IP 段 | 10.60.x | 10.67.x |
| 认证 | SRun（10.69.255.190） | Dr.COM（10.69.255.130） |
| 未认证时 | 全部 HTTP 劫持 | **直接放行到认证服务器** |
| 难度 | 复杂且被拦 | **一条明文 GET** |

板子连 `HZCU` 后，登录立刻成功：

```
result = 1
v46ip  = 10.67.229.247
uid    = YOUR_STUDENT_ID
```

**之前所有的坑，都是连错了网络。**

### 问题 25：中文响应导致 UnicodeError

板子上用 `.decode('utf-8')` 解析响应，报 `UnicodeError`——服务器返回 `charset=gbk`，里面有中文。

**解决**：直接在 bytes 上抠 JSON 字段，完全不解码。

```python
def _field(buf, key):
    k = b'"' + key.encode() + b'":'
    i = buf.find(k)
    ...
```

### 问题 26：录音 3 秒必 MemoryError

```
3 秒 → 49196 字节，要 49KB 连续块 → MemoryError
2 秒 → 32812 字节，只要 32KB      → 稳定成功
```

不是总量问题（free 显示 75KB），是**连续块**拿不到。

**解决**：默认 2 秒，失败自动降到 1 秒，并在录音前做 6~12 轮 `gc.collect()`。

### 问题 27：`f.read(512)` 返回值不定

这是「上传卡在 70%」的直接原因：

```
文件 49196 字节
f.read(512) 循环 → 只发出 44 字节就 EOF
但 Content-Length 声明 49196
→ 服务器死等剩余 49152 字节
→ 板子死等响应
→ 双方僵持
```

**解决**：用 `os.stat()` 拿准确大小，边读边发。

### 问题 28：socket 块大小

```
s.send(1024) → 直接 OSError
s.send(512)  → 327 KB/s
s.send(256)  → 425 KB/s
s.send(128)  → 弱网下最稳
```

**解决**：固定 128 字节。

### 问题 29：whisper 把提示词当答案

用了 `initial_prompt` 后，录到静音时 whisper 会把提示词原样吐出来：

```
识别结果：请使用简体中文转写。
```

**解决**：去掉 `initial_prompt`，加 `no_speech_threshold` 和 hallucination 词表过滤。

### 问题 30：弱 Wi-Fi 导致上传断

```
RSSI -78 dBm 已在临界
拿远一点 → -85 以下 → 上传到 19% 断
```

**解决**：块降到 128、单块重试 60 次、整次重传 3 轮、OLED 显示信号等级、失败时提示「弱网中断，靠近路由器」。

### 问题 31：raw REPL 比普通 REPL 更耗内存

同样的 free 值，raw REPL 执行脚本时录音失败，普通 REPL 成功。调试时踩了不少坑。

**解决**：调试录音相关代码用普通 REPL 逐行发送。
