**坑 1：出厂 `boot.py` 会删你的程序**

```python
_button_a = machine.Pin(21, machine.Pin.IN)
if _button_a.value() == 1:
    os.remove("/main.py")      # 上电瞬间 A 键按下 -> 删掉 main.py
```

本意是「应急清程序」，但我烧了贪吃蛇之后，按 A 转向 + 板子恰好重启 = 程序消失。已经换成 `board/boot_safe.py`。

**坑 2：REPL 不支持多行粘贴**

一开始用 `\r\n` 拼接多行代码发给板子，全部 `SyntaxError`。这个固件的 REPL 只吃单行；要跑多行必须 `exec(open('file.py').read())` 或走 raw REPL。

## 第一个完成的程序：贪吃蛇

选它是因为能同时验证「显示 + 按键 + 音效」三件事。

### 音频固件摸底

这块板子的音频比预想的强：

| API | 实测行为 | 能不能用 |
|---|---|---|
| `beep.time(t)` | **阻塞 643~1644 ms**（t=200 反而 889ms） | ❌ 逐帧调会卡死 |
| `music.pitch(freq, ms)` | 阻塞 ≈ ms + 65ms，`pitch(1500,30)` 只花 98ms | ✅ 游戏音效用这个 |
| `music.play(melody)` | 阻塞 0.5~3 秒 | 开/结束这类非实时场景 |

`music` 模块自带 30 首旋律：`JUMP_UP` / `POWER_DOWN` / `BA_DING` / `PUNCHLINE` / `NYAN` / `WAWAWAWAA` / `FUNERAL` / `东方红` / `义勇军进行曲` 等。

### 游戏实现要点

- 场地 32×13 格，每格 4×4 像素，顶部 12px 留分数行
- 只有 A/B 两个物理键，所以用**相对转向**（顺时针/逆时针），不是四方向
- 代码里禁止 180° 掉头（否则一按就自撞）
- 每吃 4 个加速，175ms/步 → 最快 85ms/步

**自测结果**：

```
自动演示 17 步，每帧 39ms（25fps），撞墙判定触发，死亡音效 3 声
食物从不生成在蛇身上: True
撞身体: True   撞尾巴(不吃): False   撞尾巴(吃): True
向右顺时针->2(下)   向右逆时针->0(上)   向上逆时针->3(左)
```

## 核心难题：板子联网

这是整个项目最花时间的部分。

### 方案一：板子直连 Wi-Fi

**失败。** 校园网 `YOUR_CAMPUS_SSID` 是开放 SSID，板子能拿 IP：

```
ifconfig = ('BOARD_IP', '255.255.0.0', 'CAMPUS_GW', 'CAMPUS_DNS')
```

但存在 **Portal 网页认证**，未认证时只放行 80/443 并劫持到认证页：

```
GET http://SERVER_IP/     → 200 OK
<script>location.href="http://PORTAL_IP/index_1.html"</script>
Authentication is required.
```

其他端口一律 `EHOSTUNREACH`（9446、8080、22 全挡）。

### 方案二：板子连电脑

**失败。** 同网段被 AP 隔离：

```
板子 BOARD_IP → 电脑 PC_IP:8080  → EHOSTUNREACH
```

### 方案三：电脑开热点

**部分可行。** Windows 移动热点能开，但：

```
netsh wlan show drivers → Hosted network supported: No
```

这块 Intel AX203 不能 STA+AP 同时工作。电脑一旦连板子 AP，就断外网（我因此掉线过一次）。

### 方案四：攻克 SRun Portal 认证 ← 花了最多时间

反向分析出完整协议：

```
POST/GET /cgi-bin/get_challenge?username=X&ip=Y  → 拿 token（60秒有效）
hmd5   = HMAC-MD5(key=token, msg=password)       ← 关键！
info   = {SRBX1} + base64(xxtea(json, token))
json   = {"username":U,"password":P,"ip":I,"acid":"1","enc_ver":"srun_bx1"}
chksum = SHA1(token+U+token+hmd5+token+acid+token+ip+token+"200"+token+"1"+token+info)
```

**怎么确定 hmd5 是 HMAC-MD5 的**：在浏览器控制台直接调页面的 `md5()` 函数，用三组样本对比：

```
md5('aaa','bbb')          = REDACTED_32HEX
hmac_md5('bbb','aaa')     = REDACTED_32HEX   ← 匹配
md5('aaa'+'bbb')          = REDACTED_32HEX   ← 不匹配
md5('bbb'+'aaa')          = REDACTED_32HEX   ← 不匹配
```

三组样本 + 一个真实 token 全部匹配，确定无疑。

**xxtea 和 info 也验证到 0 差异**（hook `$.base64.encode` 抓到浏览器的输入密文，同 token 同明文对比）：

```
浏览器密文长度: 104
我的密文长度:   104
差异字节数:     0 / 104
```

**但认证还是失败**，返回 `auth_info_error`。对照实验证明这跟密码无关：

```
YOUR_STUDENT_ID + 正确密码   -> auth_info_error
YOUR_STUDENT_ID + 错误密码   -> auth_info_error   ← 一模一样
不存在的账号          -> auth_info_error
```

而且**浏览器自己也失败了**：

```
浏览器(Chromium) -> login_error / "INFO failed, BAS respond timeout."
手机(真实)       -> 成功
```

结论：这套 Portal 对「脚本 / 模拟浏览器」有额外限制，`BAS respond timeout` 说明请求已到达 RADIUS 层但接入服务器无响应。算法层面已经 100% 正确，卡在服务端策略。

`board/srun_client.py` 里保留了完整实现，供以后环境变化时直接使用。

### 最终方案：USB 串口

放弃无线，回到**有线 USB**：

```
板子 ──USB串口(COM3)── 电脑 ──校园网(已认证)── 外网
```

绕开 AP 隔离、绕开 Portal 认证、也不影响电脑上网。**这条链路实测 1 秒完成往返。**

## 麦克风：一个反复打脸的排查

这部分值得单独记，因为中途我给出了错误结论。

### 第一轮：判断「麦克风坏了」（错误）

依据：

| 排查项 | 结果 |
|---|---|
| `import microphone` | ❌ 模块不存在 |
| `sound.read()` | ❌ 恒为 0（采了 40 次） |
| 录音 WAV 的分段峰值 | ❌ 恒定 325，播放语音时也只到 549 |

当时结论：GPIO37 恒读 0，其他 ADC（34/35/36/39）都正常 → 判定麦克风硬件故障。

### 第二轮：找到正确的录音接口

继续挖固件，发现真正的录音 API 在 `audio` 模块里：

```python
import audio
audio.recorder_init()
audio.record('x.wav', 3)        # 参数是 (文件名, 秒数)，最长 3 秒
audio.recorder_deinit()
```

实测生成 **49196 字节** WAV：8kHz / 16bit / 单声道 / 3.07 秒。

**坑 3：录音内存限制**

```
3 秒 -> OK 49196 bytes
4 秒 -> MemoryError（即使 gc.mem_free() 还有 75KB）
```

不是总量不够，是**堆碎片**导致拿不到连续 4KB 块。必须在录音前连做两次 `gc.collect()`。

### 第三轮：识别结果全空

把 WAV 送去 whisper，识别结果是空字符串。分析波形发现问题：

```
直流偏置: -8567          ← 整体被拉到 -8567 附近
真实信号幅度: 只有 ±330
开头 62、63 号样本: 36551（启动瞬态尖峰）
```

按绝对峰值归一化会把真实语音压到听不见。解决：**去均值 + 裁掉开头 120 个样本 + 用 95 分位数做稳健归一化**。

```python
def remove_dc_and_gain(pcm):
    mean = sum(s) // n
    centered = [v - mean for v in s]
    for i in range(min(120, n)):
        centered[i] = 0                      # 裁掉启动尖峰
    mags = sorted(abs(v) for v in centered)
    p95 = mags[int(len(mags) * 0.95)]        # 稳健峰值
    scale = 0.6 * 32767.0 / peak
    return normalized
```

处理后峰值从 330 提升到 19660，语义保留完好。

### 关于 `sound.read()` 恒为 0

`sound` 是 `ADC(Pin(37))`，而 ESP32 的 I2S 麦克风不走 ADC 通道——所以读 0 是正常的，**不能据此判断硬件损坏**。这是我第一轮的判断失误。

## 串口协议

板子和电脑之间用最朴素的行文本协议，避免二进制分帧的复杂度：

| 方向 | 格式 | 说明 |
|---|---|---|
| 板子→电脑 | `MSG\|S\|<块数>` | 开始发送 |
| 板子→电脑 | `MSG\|D\|<序号>\|<b64分片>` | 180 字节一片 |
| 板子→电脑 | `MSG\|E` | 结束 |
| 电脑→板子 | `REP\|<b64文字>` | 回答 |

**坑 4：一次性 base64 整段 WAV 会 OOM**

最初实现把 274 个分片全部转成 base64 存进 list，49KB 的 WAV 变成 65KB 字符串，超过 60KB 堆 → `MemoryError`。

改成流式：读一片、发一片、`del` 掉。

**坑 5：REPL 回显拖慢速度**

实测 250 字符/行 ≈ 27ms，274 行要 7.3 秒。这是 USB 串口 REPL 的字符回显开销，无法避免，只能减小分片数（180 字节/片是最优）。

## 固件升级的一次翻车

目录里有 `firmware-v1.06.6.5.bin`（5.8MB），想升级试试能不能修复麦克风。

```bash
esptool --port COM3 write_flash 0x0 firmware-v1.06.6.5.bin
```

**刷完板子无限重启**：

```
invalid header: 0x6d305b1b
rst:0x10 (RTCWDT_RTC_RESET),boot:0x12 (SPI_FAST_FLASH_BOOT)
```

原因：这个 5.8MB 文件不是完整的整片镜像，从 `0x0` 烧会覆盖引导区。正确做法是走 IDE 的固件升级功能，或按厂商分区表烧到 `app` 分区。

**好在提前备份了**：

```bash
esptool --port COM3 read_flash 0x0 0x800000 flash_full_backup.bin   # 8MB，MD5 D65821CC...
```

写回后板子完全恢复，文件系统和固件都正常。

**教训：刷固件前必须 `read_flash` 全片备份。**
